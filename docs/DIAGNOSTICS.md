# 流程瓶颈与异常诊断规范

- 规则集版本：`diagnostics-v1.0.0`
- 状态：阶段 6 已实现
- 更新日期：2026-08-01

## 1. 使用边界

诊断引擎把标准订单、仓库事件和物流轨迹转换为可核查线索。它回答“哪些数据事实满足了哪条规则”，不回答“经营问题一定由什么造成”。所有输出必须分成四层：

1. **数据观察事实**：时间、时长、分子分母、基线和样本；
2. **规则判断**：规则编号、版本、阈值、比较符和适用条件；
3. **可能原因**：只用“可能”“需要核查”等谨慎措辞；
4. **建议核查**：指出要回看哪些业务记录，不直接给出未经证明的处置结论。

Workers AI 或其他模型不参与本规则集的事实提取、阈值判断、严重度和订单去重。

## 2. 规则目录

默认值来自 `data/rules/diagnostic_rules.v1.json`。页面覆盖只作用于当前分析请求，不持久写回默认配置。

| 规则        | 类别           | 主要输入                               | 默认判断                                                                                             | 默认严重度                | 误报保护                                                                          |
| ----------- | -------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------- | --------------------------------------------------------------------------------- |
| `FL-WH-001` | 仓内作业延迟   | 5 个仓内完整区间、仓库                 | 接单到拣货 >4h、拣货 >2h、等待复核 >2h、复核 >1.5h、打包 >2h；或同仓节点样本 ≥10 时超过中位数 1.5 倍 | 中；超过业务阈值 2 倍升高 | 缺起止边界不计算时长；基线不足只用业务阈值并警告                                  |
| `FL-PU-001` | 出库后揽收延迟 | `ready_to_ship → carrier_picked_up`    | 完整区间严格 >12h                                                                                    | 高；超过 3 倍为严重       | 单侧事件转数据质量证据，不臆造等待时长                                            |
| `FL-LH-001` | 干线运输长尾   | `carrier_picked_up → delivered`        | 严格 >72h，或样本 ≥30 时严格超过 Type 7 P90                                                          | 高                        | 取消单排除；样本不足不启用相对分位判断                                            |
| `FL-LM-001` | 末端网点积压   | 到达目的城市、派送、签收               | 到达目的城市后等待派送/签收 >24h，派送后签收 >12h                                                    | 高                        | 只配对同运单、按 UTC 排序的完整区间                                               |
| `FL-CR-001` | 承运商相对异常 | 完成订单 OTIF、履约 P90、承运商        | 本承运商与其余承运商可比样本各 ≥30，OTIF 低 ≥10 个百分点或 P90 高 ≥25%                               | 中；两项同时命中升高      | 未知承运商、低覆盖和任一侧小样本不下群体结论                                      |
| `FL-WC-001` | 仓库拥堵观察   | 仓库、创建日期、订单量、仓内总时长 P90 | 当日订单 ≥10，历史 ≥3 日；量相对历史中位数 ≥1.25 倍且时长 P90 ≥1.2 倍                                | 中                        | 明确标注相关性；缺历史或节点样本不触发                                            |
| `FL-TC-001` | 异常时间集中   | 其他规则受影响订单的创建时间           | 异常订单 ≥10、覆盖 ≥3 个日期，星期或 6 小时时段占比 ≥50%                                             | 中                        | 单日批量数据和低样本不触发                                                        |
| `FL-DQ-001` | 事件数据异常   | 指标引擎警告、状态序列、相邻事件       | 缺失、倒序、重复、冲突、状态跳跃、`unmapped`、相邻间隔 >720h                                         | 低至高                    | 允许多枢纽、返工和 `delivery_failed → out_for_delivery`；状态跳跃只判“可能缺扫描” |

除仓库拥堵和群体差距明确使用“达到”外，时长规则使用严格大于；等于业务阈值不触发。承运商比例边界使用数值容差，避免二进制浮点把 10 个百分点误判为略小于阈值。

## 3. 证据与输出契约

每条 `DiagnosticResult` 至少包含：

- `rule_id`、`rule_version`、`title`、`category`、`severity`；
- `factual_observation`、`rule_judgement`；
- `possible_causes`、`recommended_checks`；
- `evidence`：订单/事件/运单/节点、起止时间、实际值、阈值、基线、单位和比较说明；
- `affected_order_count`、`sample_size`、`coverage`；
- `confidence_warning`；
- `dimension_type`、`dimension_value`（适用时）。

API 不返回 `NaN` 或 `Infinity`。证据列表默认截断为前 20 条，但聚合数量使用完整唯一订单集合；订单搜索接口重算相同规则并分页，因此不依赖证据样例数量对账。

## 4. 优先级、去重与对账

- 优先级：数据质量阻断 > 高严重度实际延迟 > 群体相对异常 > 相关性/集中性观察；
- 聚合：同一规则、同一节点或维度形成一个聚合结果，`affected_order_count` 按唯一订单计；
- 订单级：同一订单同一类别的多条结果合并，保留最高严重度，其他规则放入 `merged_rule_ids`，证据、可能原因和建议核查去重；
- 帕累托：每个类别使用唯一受影响订单；跨类别同一订单可分别贡献，因此累计占比的分母是“类别贡献总量”；
- 对账：`context.affected_order_count` 必须等于无筛选的受影响订单分页总数；自动化测试固定此关系。

## 5. 覆盖率与置信提示

- 订单数据覆盖率 = 有效订单数 / 唯一订单总数；
- 节点覆盖率优先使用完整区间订单数 / 具有相关边界的订单数；没有边界时为不可确定；
- 群体规则按其可比 OTIF 或时长样本计算覆盖；
- 样本小于 30、覆盖低于 80%、未提供仓库/轨迹表或关键边界缺失时，页面必须显示警告；
- “未触发”只能表示“当前数据、覆盖和阈值下未触发”，不能表述为没有问题。

## 6. API

| 方法 | 路径                                 | 用途                                       |
| ---- | ------------------------------------ | ------------------------------------------ |
| GET  | `/api/diagnostics/rules`             | 默认规则、版本、参数范围                   |
| POST | `/api/diagnostics/analyze`           | 聚合诊断、严重度、帕累托、节点、路径和维度 |
| POST | `/api/diagnostics/orders/search`     | 按严重度、类别、规则分页读取唯一受影响订单 |
| POST | `/api/diagnostics/orders/{order_id}` | 订单指标判定、合并诊断和有效事件时间线     |

POST 请求包含三类数据集 ID、IANA 时区、会话级规则覆盖和证据样例上限。未知规则、未知参数、越界阈值和非法时区使用标准错误响应。

## 7. 人工验收

1. 导入并确认订单、仓库事件和物流轨迹；
2. 打开 `/diagnostics`，确认三个数据集 ID；
3. 展开规则查看默认值，运行诊断；
4. 从帕累托选择主要类别，核对节点与维度；
5. 展开诊断项，对照事实、规则、可能原因、建议核查和证据；
6. 在受影响订单表打开时间线，核对事件顺序与原始状态；
7. 修改阈值后重算，确认版本不变、阈值只影响当前请求；
8. 运行 `python scripts/demo_diagnostics.py` 验证完全合成的五类异常和聚合—订单对账。

## 8. 已知限制

- 当前规则同步扫描所选数据集；5 万订单性能基线留到阶段 10；
- 阈值覆盖不持久保存，项目级规则配置留待设置/项目管理能力；
- 无“分析截止时间”参数，因此无法对尚未结束的开放区间计算实时等待，只报告边界缺失；
- 承运商相对比较只控制同批次、完成状态和样本/覆盖，尚未做线路、重量或服务等级匹配；
- 流程变体使用标准状态序列，不把原始同义文本视为不同变体。
