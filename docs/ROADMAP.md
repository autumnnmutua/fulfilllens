# FulfillLens 开发路线图

## 执行原则

- 按阶段 0–12 顺序推进，每一阶段先检查真实仓库状态，再实施并独立验收；
- 每阶段只完成明确范围，验收通过后才建议提交；
- 所有用户可见结论必须可追溯，所有示例数据必须完全合成；
- 本路线图中的提交信息只是建议，不代表已提交、已推送或已发布；
- 阶段成果报告必须记录真实执行的命令、失败、未执行项和遗留问题。

## 依赖主线

```text
阶段 0 → 阶段 1 → 阶段 2 → 阶段 3 → 阶段 4 → 阶段 5 → 阶段 6
                                                    └────→ 阶段 7
阶段 3–7 → 阶段 8 → 阶段 9 → 阶段 10 → 阶段 11 → 阶段 12
```

## 阶段 0：仓库初始化、环境确认与开发计划

- 依赖：无。
- 阶段成果：Git 仓库、monorepo 目录、基础忽略/换行规则、README、路线图、风险清单和 ADR 机制。
- 验收重点：结构可追踪；无密钥、真实数据、远程仓库和无关二进制；环境检查结果真实。
- 建议提交：`chore: initialize fulfilllens project structure`

## 阶段 1：产品需求、指标口径与数据规范

- 依赖：阶段 0 通过验收。
- 阶段成果：PRD、指标口径、数据字典、状态体系、架构说明、机器可读 Schema 和空白模板。
- 验收重点：OT/IF/OTIF、时效、分位数和异常率可人工复算；字段、时区、单位、敏感性和未知状态处理一致。
- 建议提交：`docs: define product metrics and data contracts`

## 阶段 2：工程骨架与基础界面

- 依赖：阶段 1 的文档、Schema 和模板通过一致性检查。
- 阶段成果：React/TypeScript/Vite 前端、FastAPI 后端、健康检查、基础路由、共享契约、质量脚本、CI 和 Docker Compose 配置。
- 验收重点：真实安装、启动、类型检查、测试和构建；360px 布局可用；失败状态不伪装成功。
- 建议提交：`feat: scaffold web api and development workflow`

## 阶段 3：数据导入、校验与字段映射

- 依赖：阶段 1 数据规范稳定；阶段 2 工程骨架可运行。
- 当前状态：本地 FastAPI 与 Cloudflare 浏览器本地路径均复用机器可读字段目录、Schema 和状态契约；在线自主 CSV/XLSX 已解除合成样例限制，原始文件不离开浏览器。
- 阶段成果：CSV/XLSX 导入向导、工作表预览、字段映射、数据质量报告、状态标准化和安全临时文件策略。
- 验收重点：UTF-8/GBK、空值、重复、非法时间、负数量、公式注入、路径遍历和大文件失败均有可定位反馈。
- 建议提交：`feat: add secure data import and field mapping`

## 阶段 4：物流履约指标计算引擎

- 依赖：阶段 3 能产生结构化、可校验的数据；阶段 1 指标口径已确认。
- 阶段成果：纯函数指标模块、总览/趋势/分布/维度/明细 API、指标元数据和金标准测试数据。
- 验收重点：OT、IF、OTIF、P50/P90、节点耗时和异常率可人工复算，聚合结果与订单明细可对账。
- 建议提交：`feat: implement fulfillment metrics engine`

## 阶段 5：分析总览与可视化仪表盘

- 依赖：阶段 2 页面框架稳定；阶段 4 指标 API 稳定且可对账。
- 阶段成果：指标卡、趋势、分布、维度对比、节点耗时、筛选、下钻和订单明细。
- 验收重点：所有数字来自真实 API；样本量、覆盖率、单位和口径清楚；桌面、移动端和键盘操作可用。
- 建议提交：`feat: build analytics dashboard and drilldowns`

## 阶段 6：流程瓶颈与异常诊断引擎

- 依赖：阶段 4 指标稳定；阶段 5 可追溯到订单明细。
- 当前状态：已实现 `diagnostics-v1.0.0`、8 类透明规则、会话级阈值覆盖、帕累托、瓶颈节点、流程变体、维度下钻、受影响订单分页和事件时间线；云部署仅完成可行性评估，未部署。
- 阶段成果：版本化透明规则、订单时间线、聚合异常、帕累托分析、流程变体和证据下钻。
- 验收重点：事实、规则判断和可能原因分层；规则含阈值、证据、严重度和样本警告；重复触发合理去重。
- 建议提交：`feat: add explainable logistics diagnostics`

## 阶段 7：What-if 改进方案模拟器

- 依赖：阶段 4 指标引擎可复用；阶段 6 能定位主要瓶颈。
- 当前状态：已实现 `simulation-v1.0.0`、只读基线、SQLite 多方案、仓内/揽收/承运商结构/承诺策略、订单证据、固定种子经验重采样和单参数敏感性分析；末端、节假日、成本和容量模型未实现。
- 阶段成果：基线与多方案、参数校验、订单/节点层变换、指标重算、敏感性分析和模拟说明。
- 验收重点：不修改原始数据；结果可复现；参数有单位与范围；所有结果显著标注为情景估算。
- 建议提交：`feat: implement what-if scenario simulator`

## 阶段 8：合成数据与教学案例

- 依赖：阶段 3–7 的导入、指标、诊断和模拟主流程可工作。
- 当前状态：已实现 `case-generator-v1.0.0`、三套固定种子数据、CSV/XLSX/metadata、中文教材、一键载入和全链路回归；指标容差与规则触发均对真实生成结果断言。
- 阶段成果：可配置数据生成器、正常运营/促销爆单/承运商异常三套案例、案例教材和回归测试。
- 验收重点：无真实个人信息；固定种子可复现；Schema、时间顺序、指标范围和规则触发均由测试验证。
- 建议提交：`feat: add reproducible teaching datasets and cases`

## 阶段 9：分析报告与结果导出

- 依赖：阶段 5–8 的分析、诊断、模拟和案例结果稳定。
- 当前状态：已实现 `report-v1.0.0`、可选章节预览、筛选一致的 Markdown/自包含 HTML、五类安全 CSV、标识二次确认、异步进度/取消和合成示例报告；PDF 因本机无 Docker、未验证中文字体与分页而保持不可用。
- 阶段成果：报告预览、Markdown/HTML 主路径、安全 CSV 导出，以及环境可靠时的 PDF。
- 验收重点：报告与当前筛选和页面/API 对账；事实、判断、可能原因和模拟分层；中文、长表、文件名和公式注入安全。
- 建议提交：`feat: add analysis reports and safe exports`

## 阶段 10：专项测试、安全、性能与可访问性

- 依赖：阶段 2–9 的全部 MVP 能力基本完成。
- 当前状态：已完成数据清理、首次使用者解释、三条端到端流程、依赖/输入/导出安全复验、三档 Chromium + axe 审计，以及 1 万/5 万单性能基线；阶段 10 当时缺少 Docker，现已在阶段 12 的 Windows 重启后实机复验中补齐。Firefox/Safari 未验证。
- 阶段成果：测试矩阵、缺陷修复、性能基线、安全与隐私检查、移动端和可访问性改进。
- 验收重点：全量检查真实通过；目标数据规模下无明显卡死或失控；不存在高严重度安全问题和被跳过的关键测试。
- 建议提交：`test: harden quality security performance and a11y`

## 阶段 11：开源文档与 GitHub 发布准备

- 依赖：阶段 10 的本机质量门禁通过；Docker 与跨浏览器保留为明确的阶段 12 发布验收项。
- 当前状态：已完成中英文 README、MIT 与依赖许可审查、贡献/安全/行为准则、FAQ/故障排查、Issue/PR 模板、截图清单、文档/隐私/许可证检查；GitHub 公开远程、Private Vulnerability Reporting、质量/Docker smoke 和 Cloudflare 合成在线演示均已完成。
- 阶段成果：中英文 README、许可证、贡献/安全/行为准则、Issue/PR 模板、变更日志、发布候选说明和发布前 CI。
- 验收重点：陌生用户可按真实命令在 10 分钟内载入示例；依赖许可证兼容；仓库无敏感信息和本地产物。
- 建议提交：`docs: prepare open-source release assets`

## 阶段 12：最终全量审查与 v1.0 验收

- 依赖：阶段 0–11 全部完成，发布候选资料齐全。
- 阶段成果：全流程复验、人工复算、最终缺陷修复、`docs/RELEASE_ACCEPTANCE.md` 和明确发布结论。
- 验收重点：干净环境安装、三套案例端到端、全量质量命令、安全隐私和文档一致性；任何阻断项必须如实阻止发布。
- 建议提交：`release: prepare fulfilllens v1.0.0`
- 当前状态：`1.0.0-rc.5` 增加字段映射可读布局、显式 ignored/unresolved 语义和必填防绕过，并把公开品牌迁移为 FulfillLens；最终发布以本机全量检查、Docker、Cloudflare 新域名线上复验和相同提交上的 GitHub Actions 成功结果为准。浏览器自有数据接入 Worker 分析仍为后续明确事项。

## 提交与回滚约定

- 每个阶段建议至少形成一个范围单一、可审查的本地提交；
- 提交前保存实际验证结果，不把“计划运行”写成“已经通过”；
- 不在阶段任务中自动创建远程、推送、打标签或部署；
- 发现回归时修复根因并增加测试，不通过删除功能或降低断言回避失败。
