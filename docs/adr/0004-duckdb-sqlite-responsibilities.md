# ADR-0004：DuckDB 与 SQLite 职责分离

- 状态：Accepted
- 日期：2026-07-29
- 取代：无

## 背景

订单和事件明细适合列式分析，映射、任务和方案配置则需要轻量事务。将两类负载放入同一存储会增加查询复杂度，或导致大量明细在 SQLite 中效率不足。

## 决定

- DuckDB 作为分析数据平面，保存/查询规范化订单、事件、派生情景和分析中间关系；
- SQLite 作为控制平面，保存数据集元数据、导入任务、映射、规则配置、情景参数和本地设置；
- Pandas 用于受控规模的解析、清洗和领域计算，不默认一次性加载全部明细；
- API 通过存储服务访问两类数据库，路由和前端不依赖物理表；
- 模拟派生关系与基线隔离；
- 两类数据库文件均为本地可清理数据，不提交 Git。

## 理由

- DuckDB 适合本地列式扫描、联接、聚合和分位数输入；
- SQLite 适合小规模事务配置和任务状态；
- 职责分离让数据生命周期和性能边界更清晰；
- 两者均为进程内、本地优先技术。

## 后果

- 需要明确数据集与控制元数据的一致性恢复策略；
- 清理任务必须同时处理 DuckDB、SQLite 记录和文件；
- 阶段 2/3 需要定义事务边界和失败补偿；
- 不能用 SQLite 表直接替代分析层。

## 替代方案

- 仅 SQLite：简单，但大规模分析和列式查询能力不足；
- 仅 DuckDB：分析强，但任务与配置事务模型不够清晰；
- 外部 PostgreSQL：成熟但违反 MVP 的低门槛本地优先目标。

## 复审条件

- 真实性能测试显示双存储开销不可接受；
- 多进程并发需求超出文件型数据库能力；
- 出现可靠、简单且兼顾事务与分析的新单一方案。
